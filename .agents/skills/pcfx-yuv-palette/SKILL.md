# Colour: the HuC6261 YUV palette

**The PC-FX palette is YUV, not RGB.** This is the single most common colour mistake.
There are 256 palette entries in the Tetsu/VCE chip, each a 16-bit word:

```
 Y8U4V4:   (Y << 8) | (U << 4) | V
           Y = luma,      8 bits, 0..255
           U = blue diff, 4 bits, 8 = neutral
           V = red diff,  4 bits, 8 = neutral
```

So `0x8088` is mid grey, `0xFF88` is white, `0x0188` is black. `U = V = 8` means no
chroma. **Do not hand-guess colour constants** — Y8U4V4 is not intuitive, and a
plausible-looking value renders a completely different hue. (While writing this skill,
`0x8030` was guessed as "blue" and rendered pure green.)

## Use the converter

```bash
python3 PCFX_Skills/pcfx-yuv-palette/rgb_to_yuv.py 255 0 0     # one colour
python3 PCFX_Skills/pcfx-yuv-palette/rgb_to_yuv.py --table     # 16-colour starter set
```

A verified starter palette (generated by that script, confirmed on screen):

```c
tetsu_set_palette( 0, 0x0188);  /* black      */
tetsu_set_palette( 1, 0x4088);  /* dark grey  */
tetsu_set_palette( 2, 0x8088);  /* grey       */
tetsu_set_palette( 3, 0xC088);  /* light grey */
tetsu_set_palette( 4, 0xFF88);  /* white      */
tetsu_set_palette( 5, 0x506F);  /* red        */
tetsu_set_palette( 6, 0x277D);  /* dark red   */
tetsu_set_palette( 7, 0x9730);  /* green      */
tetsu_set_palette( 8, 0x4A64);  /* dark green */
tetsu_set_palette( 9, 0x1DF6);  /* blue       */
tetsu_set_palette(10, 0x9AB5);  /* light blue */
tetsu_set_palette(11, 0xE31A);  /* yellow     */
tetsu_set_palette(12, 0x9F3D);  /* orange     */
tetsu_set_palette(13, 0x69DF);  /* magenta    */
tetsu_set_palette(14, 0xB2A0);  /* cyan       */
tetsu_set_palette(15, 0x646A);  /* brown      */
```

## The conversion, and why it is a search

The hardware reconstructs RGB from YUV as:

```
u = (U4 << 4) - 128 ;  v = (V4 << 4) - 128
r = Y + (1167*v)/1024
g = Y + (-404*u - 594*v)/1024
b = Y + (2081*u - v)/1024      (then clamp each to 0..255)
```

Because U and V have only 4 bits, most RGB colours are not exactly representable. The
converter seeds analytically, then searches a ±3 window in U4/V4 (and a small Y range),
scoring with a **green-weighted** error metric (`2*dr² + 4*dg² + db²`) because the eye is
most sensitive to green error.

Two rules that came out of doom-pcfx's colour work:

- **`forbid_grey`**: if the source colour has any real saturation (`max-min >= 8`), the
  neutral point `U4=V4=8` is excluded. Without this, dark saturated colours collapse to
  grey — the "browns speckle grey" bug.
- **Y = 0 is special.** Prefer `Y = 1` for black (hence `0x0188`); some paths treat
  index 0 / Y 0 as transparent.

If you bake palettes at build time, the Python and the C **must be bit-identical**, or
colours drift between your asset tool and runtime. wolf-pcfx keeps only the YUV table and
*reconstructs* RGB from it when the engine needs `.r/.g/.b`, rather than keeping two
tables that can disagree — do that.

## Palette layout across layers

The 256 entries are shared by every layer. Each layer gets a **base offset** into the
palette, so layers carve it up:

```c
tetsu_set_king_palette(bg0, bg1, bg2, bg3);  /* base entry per KING BG   */
tetsu_set_vdc_palette(vdcbg, vdcspr);        /* base entry per VDC use   */
tetsu_set_rainbow_palette(rainbow);          /* base entry for RAINBOW   */
```

A KING BG0 8bpp bitmap wants all 256 entries at base 0. If you also need VDC sprites or
RAINBOW, they must live in a sub-range — e.g. descent-pcfx puts RAINBOW at base 256 and
leaves 0..255 to BG0; emeraldpcfx puts VDC object palettes at 256+ in groups of 16.
Plan this before you bake art.

VDC layers use 16-colour sub-palettes: a tile/sprite names a **palette group**, and all
its pixels must fall in that group's 16 entries. emeraldpcfx draws 8bpp GBA objects on the
VDC only when every pixel in a cell falls inside one 16-entry group; cells that straddle
two groups have nowhere to go.

## Index 0 is transparent

Colour index 0 is transparent for compositing. Art that legitimately uses index 0 as a
real colour must be remapped to another index at bake time, or it will show through. This
bit doom-pcfx's WAD assets.

## When it is safe to write the palette

**Write palette entries during vertical blanking.** A 256-entry burst during active
display causes visible glitches; both wolf-pcfx (`video: keep VCE palette and KING mode
writes out of active display`) and doom-pcfx (`video: flush VCE palette during blanking`)
shipped fixes for exactly this. See [pcfx-frame-timing].

Converting a whole palette at runtime is expensive: doom-pcfx measured ~8 ms/frame plus
114–156 ms freezes from doing RGB→YUV searches during gameplay. **Pre-convert every
palette you will need**, at build time or at load time, never in the frame loop.
