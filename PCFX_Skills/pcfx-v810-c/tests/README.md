# C code-generation probe

This is a small, reproducible check of ordinary C code generated by the bundled
V810 GCC. It is evidence for this pinned compiler/configuration, not a benchmark and
not a guarantee about every source context.

Run from the toolkit root:

```sh
PCFX_V810_GCC="$PWD/toolchain/v810-gcc" \
    PCFX_Skills/pcfx-v810-c/tests/run_codegen_probe.sh
```

The generated assembly is written to `build/pcfx-v810-c-probe.s`. The captured
GCC 4.9.4 output in `reference-output-gcc-4.9.4.s` is a review aid; the runner checks
stable instruction patterns rather than requiring byte-for-byte output.

The source covers signed/unsigned byte and halfword reads, narrow argument promotion,
signed/unsigned comparisons, low-word multiplies, variable division and remainder,
constant division, shifts, sequential sum loops, 32×32-to-64 and 64×64 multiplication,
and defined unsigned wraparound.

With GCC 4.9.4 and `-O2 -mv810 -msda=256 -mno-prolog-function`, the asserted patterns
are:

- Signed byte/halfword pointer reads use `ld.b`/`ld.h` directly.
- Unsigned byte/halfword pointer reads use `ld.b`/`ld.h` and an `andi` zero-extension.
- Both low-word 32-bit multiply functions use `mul` in this probe.
- Signed and unsigned divide/remainder use `div` and `divu`, respectively.
- Both the `uint32_t`-by-`uint32_t` product widened to `uint64_t` and the
  `int64_t`-by-`int64_t` product call `___muldi3`.

Other observations to inspect in the output rather than treating as global rules:

- `less_s32` and `less_u32` use signed and unsigned conditions.
- `add_s16` and `add_u16` need different argument normalization; this toolchain's
  unsigned example is shorter.
- In this probe, division by the constant 10 still uses `DIV`/`DIVU` after materializing
  the divisor. Do not assume constant division is strength-reduced on this GCC.
- The two widened multiplication cases both call `___muldi3`; keep checking the exact
  compiler output when source widths or build flags change.

The C cases are intentionally simple functions so that the assembly can be compared
function by function. The probe runner checks semantic patterns, not exact registers or
instruction scheduling.
