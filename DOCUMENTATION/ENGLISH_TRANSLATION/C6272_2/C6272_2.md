# HuC6272 Functional Description

# Chapter 3: Functional Operation

This document expands the block-level behavior summarized in the HuC6272 overview and register manual.

## 3.1 CPU interface

### 3.1.1 Master-bus interface

- Data bus width: 16 bits.
- The HuC6272 is enabled by its own independent chip-select signal.
- Register and KRAM accesses are distinguished by address and control signals.
- The CPU must observe the device-ready/busy timing for accesses that require K-BUS ownership.
- Use aligned 16-bit accesses. Reserved address combinations are not defined.

### 3.1.2 CPU access to KRAM

CPU KRAM access is indirect. Software first programs the CPU KRAM read or write address and the applicable page, then transfers words through the KRAM data register. Read and write pointers are independent and may auto-increment.

KRAM is shared with the display, SCSI, HuC6271, and HuC6230 engines. CPU service can therefore be delayed by higher-priority traffic. Do not start a new transaction while the HuC6272 indicates that the prior one is incomplete.

An access must remain inside the selected page/bank. Software must explicitly reload the address and page before crossing a boundary.

### 3.1.3 KRAM-access registers

The relevant registers are CPU write address (`REG.0C`), CPU read address (`REG.0D`), KRAM data (`REG.0E`), KRAM page (`REG.0F`), and KRAM mode (`REG.61`). Their bit definitions are given in the register-specification document.

## 3.2 K-BUS controller

### 3.2.1 Overview

The K-BUS controller arbitrates all KRAM requests and generates DRAM timing and refresh. Request priority depends on whether the video output is in active display or blanking.

### 3.2.2 Arbitration priority

During active display:

`BG > HuC6271 > SCSI > CPU`

During horizontal/vertical blanking:

`Refresh > ADPCM > HuC6271 > SCSI > CPU`

The background engine receives highest priority during active display so that visible pixels are not starved. ADPCM service is concentrated in blanking intervals to maintain the programmed audio rate without stealing display bandwidth. CPU access has the lowest priority and must tolerate variable wait time.

### 3.2.3 Refresh control

KRAM refresh is generated automatically. Refresh receives highest priority during blanking and is interleaved so that the guaranteed DRAM refresh interval is met. Software must use the supported KRAM organization and clock; no manual refresh command is required.

## 3.3 SCSI interface

### 3.3.1 Overview

The on-chip SCSI block provides initiator-side bus control, phase/status observation, interrupt reporting, direct DMA into KRAM, pseudo-DMA through the CPU, and CD-ROM subcode reception.

The controller does not replace the complete SCSI protocol state machine in software. The host must still issue the correct selection, command, data, status, and message operations and respond to exceptional phases.

### 3.3.2 SCSI registers

The SCSI register group includes current data, initiator command, mode, target command, current bus status, bus-and-status, input data, reset/interrupt, subcode control/data, DMA control, and transfer count. Program only fields valid for the current SCSI phase.

### 3.3.3 SCSI interrupts

Interrupt sources include bus reset, phase mismatch or phase change, selection/reselection events, DMA completion, and subcode reception. The status register identifies the active cause. Service the SCSI condition first, then clear the corresponding interrupt latch.

### 3.3.4 DMA transfer from SCSI to KRAM

A DMA transfer is prepared by:

1. Selecting the KRAM page and destination address.
2. Loading the transfer count.
3. Programming the SCSI mode and expected bus phase.
4. Enabling DMA.
5. Completing or accepting the relevant SCSI handshake.
6. Waiting for the DMA-complete or SCSI-exception status.

The controller writes incoming 8-bit SCSI data into 16-bit KRAM storage in the documented packing order. Transfer count and destination address advance automatically. A phase change, reset, or count completion terminates the active operation as defined by the SCSI control bits.

Do not let a DMA transfer cross an unsupported KRAM page boundary. Split a large transfer into multiple operations when necessary.

### 3.3.5 KRAM storage of SCSI data

Bytes are packed into KRAM words in the device-defined order. Even and odd byte positions are paired into one 16-bit KRAM word. If a transfer has an odd byte count, software must treat the unused byte of the final word according to the documented packing convention rather than assuming it is preserved.

### 3.3.6 Pseudo-DMA mode

Pseudo-DMA lets the CPU move SCSI data through the HuC6272 data path while the SCSI block performs the bus handshake. It is intended for short transfers, diagnostic operation, and cases where direct KRAM DMA is inconvenient.

The CPU must service the data-ready condition at the required rate. Overrun or underrun can occur if software fails to read or write the pseudo-DMA port before the next handshake event.

### 3.3.7 Subcode reading

CD-ROM subcode data is captured under control of the subcode-control register. The status register indicates when a new subcode datum is available. Read the subcode data register before acknowledging/clearing the event so that the next datum is not lost.

## 3.4 HuC6271 data-transfer block

### 3.4.1 Related registers

Transfer control, KRAM start address, start raster, block count, and raster monitor are programmed through `REG.40–REG.44`.

### 3.4.2 Compressed-image transfer control

#### Normal playback

Program one continuous KRAM source and block count, select the start raster, and enable transfer. The source advances as blocks are accepted by the HuC6271. A new source/count written during transfer is reserved for the next operation where specified.

#### Scrolling playback

For source material organized as a scrolling stream, update the KRAM start address and block count at the documented frame or raster boundary. Use raster monitoring to avoid changing the source while the current block is being consumed.

#### Split playback

A frame can be divided into regions with different compressed-data streams. Program the first transfer, monitor the split raster, and then stage the source/count for the following region. The transfer-start timing must leave enough time for HuC6271 input buffering.

#### Dummy data

When required by the HuC6271 data protocol, insert the specified dummy words/blocks at stream boundaries. Dummy data is part of the KRAM layout and must be included in address/count calculations.

## 3.5 HuC6230 ADPCM transfer

### 3.5.1 Overview

Two independent channels move encoded ADPCM data from KRAM to the HuC6230. The HuC6230 determines the sample clock; the HuC6272 supplies encoded nibbles/bytes at the corresponding request rate.

### 3.5.2 Playback procedure

1. Store ADPCM data in KRAM using the required 16-bit word packing.
2. Program each channel’s start, half, and end addresses.
3. Select ring or sequential operation.
4. Configure the HuC6230 sampling frequency and interpolation.
5. Clear stale half/end status.
6. Enable the HuC6272 buffer and the HuC6230 decoder.
7. Refill the consumed half of a ring buffer after each half/end event.

Supported nominal sample rates are 31.47, 15.73, 7.87, and 3.93 kHz. Encoded transfer bandwidth scales with the selected rate and the ADPCM bit rate.

### 3.5.3 Related registers

`REG.50–REG.5E` contain common control, per-channel buffer control, status, and start/end/half addresses.

### 3.5.4 KRAM-to-HuC6230 transfer

The HuC6272 reads the current channel pointer, transfers the next encoded datum when requested, and advances the pointer. In ring mode the pointer wraps at the end address. In sequential mode the engine stops and sets the end status. The half event is generated when the half address is crossed, allowing software to refill the inactive half.

### 3.5.5 KRAM data format

HuC6230 ADPCM data is stored as 16-bit KRAM words. Preserve the documented nibble/byte order when generating streams; reversing the order produces incorrect sample reconstruction. Align buffer boundaries to whole KRAM words.

## 3.6 Background processor

### 3.6.1 Operation

For every raster, the background processor derives the source coordinates for each active plane, fetches BAT/CG or direct pixel data from KRAM, resolves transparency, applies priority, and sends the resulting natural-picture pixel stream to the HuC6261.

The microprogram determines the fetch schedule. A valid schedule must fit inside the KRAM service budget for the selected color depths and number of planes.

### 3.6.2 Related registers

The BG register group includes plane format and priority, microprogram load/control, subplane cylindrical mode, BAT/CG base addresses, plane sizes, per-plane scroll values, and BG0 affine parameters.

### 3.6.3 Plane operating formats

#### Internal dot-sequential format

Pixel data is stored directly in KRAM in the native color depth. The BG processor computes a linear source address from plane size, scroll, and optional affine parameters.

#### External block format

A BAT identifies blocks/characters, and CG data holds the pixel patterns. This permits repeated tiles and more compact scenes.

#### External dot-sequential format

Pixel values are externally organized as a dot stream but use the high-color formats supported by the background datapath.

#### Subplanes

Large logical planes may be built from subplanes. The subplane table controls which source region is used for each area. Cylindrical mode repeats the pattern; transparent-paste mode supplies transparent pixels outside the defined region.

### 3.6.4 Display data

The meaning and byte/word layout of KRAM data depend on the selected color mode. Palette modes carry an index; direct-color modes carry luminance/chrominance or direct color components as defined by the HuC6261 interface. Base addresses must meet the alignment implied by the BAT/CG address registers.

### 3.6.5 Special processing

Supported effects include:

- Independent per-plane scrolling.
- Raster splits by rewriting scroll/priority/format at HSYNC boundaries.
- BG0 affine rotation, enlargement, and reduction.
- Repeated cylindrical subplanes.
- Transparent color suppression.
- Plane enable/disable and front-to-back priority composition.

For affine BG0, use signed 8.8 coefficients and calculate the center terms so that the desired screen point remains fixed during rotation or scaling.

### 3.6.6 Reprogramming during display

Scroll values become effective from the next HSYNC. Other immediate registers act as soon as written. To avoid partial-line artifacts, perform updates in horizontal blanking or use a raster interrupt/monitor with sufficient setup margin.

When changing several related parameters, disable the plane or stage the writes during vertical blanking so that no line observes a mixed configuration.

### 3.6.7 Microprogram

The BG microprogram is a short sequencer program that schedules plane reads and output operations. Load it only while `MPSW = 0`, then enable it with `MPSW = 1`.

A microinstruction selects a plane/source operation and controls continuation/termination. The exact bit fields and timing diagrams are retained in the source figures below. The program must:

- Fetch every enabled plane at the required cadence.
- Respect KRAM access latency for the selected format.
- Produce pixels in the order expected by the priority compositor.
- End or loop at the correct raster position.
- Leave sufficient bandwidth for mandatory non-BG operations.

### 3.6.8 Single-plane examples

For one active plane, the program contains only the fetch and output steps required by that plane’s format. High-color modes require more KRAM cycles per pixel than indexed modes and therefore use a different sequence.

### 3.6.9 Multiple-plane examples

For multiple planes, interleave their fetches so that each plane’s next pixel is ready before composition. The examples show schedules for common combinations of indexed and direct-color planes. Do not simply concatenate independent single-plane programs; the combined program must satisfy the shared K-BUS timing budget.
